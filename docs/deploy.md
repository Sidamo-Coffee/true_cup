# デプロイ手順（Render + Neon）

無料枠のサービスを組み合わせた構成で公開する手順。全体の構想は #154。

## 構成

| 役割 | サービス | 接続方法 |
| --- | --- | --- |
| Web サーバー | Render（Web Service / Free） | `render.yaml` |
| データベース | Neon（PostgreSQL / Free） | `DATABASE_URL` |

**Render の無料 PostgreSQL は作成から30日で期限切れになる**ため使わない。
DB を Neon に置くことで、サービスを作り直しても記録が残る。

## 事前に用意するもの

- GitHub アカウント（このリポジトリへのアクセス）
- Render のアカウント
- Neon のアカウント
- `config/master.key` の中身（このリポジトリには含まれない。手元の作業ディレクトリにある）

## 手順

### 1. Neon でデータベースを作る

1. Neon でプロジェクトを作成する（リージョンは Singapore が近い）
2. 接続文字列（Connection string）をコピーする
   - **プール接続（ホスト名に `-pooler` が付くもの）ではなく、直接接続を選ぶ。**
     プール接続は PgBouncer の transaction mode で動くため、`SET` や一時テーブル、
     セッションレベルの advisory lock が使えない。単一インスタンスの規模では利点が無い
   - `?sslmode=require` などのパラメータが付いた形のまま使う

接続文字列にはパスワードが含まれる。**Issue・PR を含め、どこにも貼らない。**
このリポジトリは public で、GitHub は本文の編集履歴を保持するため、後から消しても取り消せない。

### 2. Render で Blueprint を読み込む

1. Render のダッシュボードで **New → Blueprint**
2. このリポジトリを Connect する。続けて Blueprint の名前と、対象ブランチ（`main`）を選ぶ。
   `render.yaml` が読み込まれる
3. 環境変数の入力を求められるので、次の2つを入れる

   | キー | 値 |
   | --- | --- |
   | `RAILS_MASTER_KEY` | `config/master.key` の中身 |
   | `DATABASE_URL` | 手順1でコピーした Neon の接続文字列 |

4. Apply でサービスが作られ、初回のビルドが始まる

`RAILS_ENV` / `NODE_VERSION` / `WEB_CONCURRENCY` は `render.yaml` に書いてあるため入力不要。

`render.yaml` はリージョンを `singapore` にしている（日本から近いため）。
無料プランが選べないと言われた場合は `region: oregon`（Render の既定）に変えて試す。
**リージョンは作成後に変更できない**ため、変える場合はサービスを作り直すことになる。

### 3. メール送信を設定する（任意だが、しないとパスワードリセットができない）

Devise のパスワードリセットはメールで届く。**SMTP を設定しないとメールが送られない。**
画面はエラーにならず「再設定用のメールを送りました」と表示されるだけなので、気づきにくい。

利用者が自分だけで、パスワードを忘れる心配が無いなら後回しでよい。
その場合、パスワードを忘れたときは `bin/rails console` で直接変更することになる
（無料プランではシェルが使えないため、手元から Neon に接続して行う）。

設定する場合は、Render のダッシュボードで次の環境変数を足す。
どの SMTP サービスでも動くようにしてあるため、無料枠のあるサービスを選べばよい。

| キー | 内容 |
| --- | --- |
| `SMTP_ADDRESS` | SMTP サーバーのホスト名。**これが設定されたときだけ送信を行う** |
| `SMTP_PORT` | ポート（省略時は 587）。`465` を指定すると接続時から TLS になる |
| `SMTP_USER_NAME` | ユーザー名 |
| `SMTP_PASSWORD` | パスワード / API キー |
| `SMTP_AUTHENTICATION` | 認証方式（省略時は `plain`）。`login` / `cram_md5` も指定できる |
| `MAILER_SENDER` | 差出人アドレス。**SMTP の送信元に合わせて必ず設定する**。既定値のままだと多くのサービスが送信を拒否する |

`SMTP_ADDRESS` を設定してから送信に失敗した場合は、**画面が 500 になり例外がログに残る**。
設定したのに届かないという状態を黙って進めないため、あえてそうしている。

メール本文の URL のホストは、Render が自動で渡す `RENDER_EXTERNAL_HOSTNAME` を使う。
独自ドメイン（#88）に移したら `APP_HOST` を設定して上書きする。

### 4. デプロイの確認

ビルドログとサービスログで次を確認する。

- [ ] ビルドが成功する（`bin/render-build.sh` が `bundle install` → `yarn install` →
      `assets:precompile` → `db:migrate` の順に流れる）
- [ ] 起動ログに `Puma version:` と `Listening on http://0.0.0.0:<PORT>` が出る
- [ ] ヘルスチェック `/up` が 200 を返す（Render は 3xx も healthy と扱うため 301 でも通るが、
      200 なら SSL リダイレクトの除外が効いていることまで確認できる）
- [ ] トップページ、ログイン、味覚診断、記録の一覧が表示できる
- [ ] **スマートフォンから開いて崩れが無い**（このアプリは主にスマホから使われる）
- [ ] SMTP を設定したなら、パスワードリセットのメールが届き、リンクのホストが正しい

## 2回目以降

`main` にマージすると自動でデプロイされる。手作業は不要。

## 運用上の注意

### 15分でスリープする

無料の Web サービスは **15分アクセスが無いとスリープし、次のアクセスで復帰に約1分**かかる。
久しぶりに開くと最初の表示が遅いが、故障ではない。

無料枠は月 750 インスタンス時間。使い切ると翌月まで停止する。

### Neon も一定時間でサスペンドする

Neon の無料枠のコンピュートは**5分の無操作でサスペンド**し、次のクエリで復帰する。
無料プランではこの自動サスペンドを無効にできない。
Render のスリープ復帰と重なるため、最初のアクセスはさらに待つことがある。

### スリープ対策に定期 ping をしてはいけない

「15分でスリープするなら定期的に叩けばよい」と考えたくなるが、**この構成では破綻する。**

Neon の無料枠は **100 CU-hours/プロジェクト・月**（0.25 CU なら約400時間）で、
使い切ると次の請求期間まで**コンピュートがサスペンドされる**。
常時起動させると月 730 時間になり、月半ばで DB 側が止まる。データは残るが読み書きができなくなる。

Render 側も月 750 インスタンス時間で、こちらも使い切ると停止する。
**スリープは仕様として受け入れる**のが、この構成の前提になる。

### 永続ディスクが無い

無料の Web サービスは永続ディスクを使えない。デプロイのたびにファイルシステムは作り直される。

現在 Active Storage の添付は1件も無いため実害は無いが、
**#94（写真添付）を実装する前に、保存先を Cloudflare R2 に移す必要がある**（#154 の段階2）。

## 困ったときに見るところ

| 症状 | 見るところ |
| --- | --- |
| ビルドが落ちる | Render のビルドログ。`yarn install` と `assets:precompile` の行 |
| 起動後すぐ落ちる | サービスログ。`DATABASE_URL` の誤りは接続エラーで出る |
| ヘルスチェックは通るのに全ページが 500 | **`/up` は DB を見ない。** Neon の使用量（CU-hours）が枯渇していないか |
| パスワードリセットのメールが届かない | `SMTP_ADDRESS` 未設定なら送信自体を行わない。画面もログも静かなので設定漏れを疑う |
| パスワードリセットで 500 になる | SMTP は設定済みで送信に失敗している。例外がログに出ているので内容を見る |
| リダイレクトが繰り返される | `config.force_ssl` と `config.assume_ssl` の関係を疑う |
| ヘルスチェックが通らない | `/up` のレスポンス。除外は完全一致のため `/up/` は 301 を返す点に注意 |

## 切り戻し

Render のダッシュボードから直前の成功デプロイへ rollback できる（再ビルド不要）。

**ダッシュボードで rollback すると自動デプロイが無効になる。**

> Triggering a rollback in the Render Dashboard automatically disables autodeploys for the service.
> （[Render Docs / Rollbacks](https://render.com/docs/rollbacks)）

原因を直したあと、**Settings で自動デプロイを再度有効にする**まで、`main` にマージしても何も起きない。

コード側の問題であれば `git revert` してマージすれば、自動デプロイで戻る（有効になっていれば）。

**ただし migration は戻らない。** `bin/render-build.sh` はビルドの中で `db:migrate` を実行するため、
ビルドが成功して起動だけ失敗した場合、DB のスキーマは新しいまま残る。
rollback したリビジョンが新しいスキーマと噛み合わない可能性がある。
破壊的な migration（カラム削除・型変更）を入れるときは、この点を踏まえて手順を決めること。
