# PR のレビューをサブエージェントに依頼する

## なぜやるか

自分が書いたコードを自分で見直しても、**同じ思い込みのまま読んでしまう**ため見落としが残る。

一方で、**情報漏洩に関してはレビューは最後の網でしかない**。公開は PR 作成の時点で成立しており、
事後の編集では回収できない。書かないことが第一。

## 実行回数の上限

**このスキルは、ユーザーが明示的に `/pr-review` を実行したときだけ動かす。**
PR を作成しただけでは起動しない。

| | 条件 |
| --- | --- |
| 1回目 | 通常のレビュー。**これで終わり** |
| 2回目 | 1回目で**重大な問題**が指摘され、その修正を行った場合に**限り**1回だけ |
| 3回目以降 | **行わない** |

- **改善提案・任意対応・好みの問題しか出なかった場合は、再レビューしない。**
  対応するかどうかを自分で判断し、PR 本文に記録して終える
- 2回目で新しい指摘が出ても、**自動的に3回目を始めない。**
  残っている指摘をユーザーに報告し、どうするか判断してもらう

## 手順

### 1. サブエージェントを起動する

`Agent` ツールで `subagent_type: general-purpose`、`run_in_background: false` を指定する。
同期実行にするのは、レビュー結果を見てから次に進む必要があるため。

プロンプトには次を必ず含める。

- **シニアエンジニアとして振る舞う**よう指示する
- 対象の PR 番号と作業ディレクトリ
- 調べ方（下記のコマンド）
- レビュー観点（下記）
- 出力形式（下記）
- **推測で書かず、実際に確認した内容だけを述べる**よう指示する

調べ方として渡すコマンド:

```
gh pr view <N> --repo Sidamo-Coffee/true_cup --json title,body --template '{{.title}}{{"\n"}}{{.body}}'
gh pr diff <N> --repo Sidamo-Coffee/true_cup
gh issue view <対応するIssue番号> --repo Sidamo-Coffee/true_cup --json body --template '{{.body}}'
```

CLAUDE.md を読ませてプロジェクトの方針を把握させること。特に「Issue / PR に書いてはいけないもの」と
プロダクト概要（想定ユーザーはコーヒー初心者）は判断の前提になる。

**挙動を実際に確かめられることを伝える**と精度が上がる。机上の判断だけでは分からない問題が拾える。

```
docker compose exec -T web bash -c "RAILS_ENV=test bin/rails runner tmp/probe.rb"
```

スクリプトは `tmp/` に置き、`ActiveRecord::Base.transaction` + `raise ActiveRecord::Rollback` で
後始末し、確認後は削除するよう指示する。

### 2. レビュー観点

毎回渡す基本の観点:

- **公開すべきでない情報が PR 本文・差分に含まれていないか。** リポジトリが public であることを明示する
- **PR 説明の記述が実際の差分・挙動と食い違っていないか。** 特に PR 本文に貼った実行結果やシナリオが
  実際に再現するか、疑わしければ自分で実行して確かめるよう指示する
- 変更範囲が Issue のスコープを超えていないか、逆に必要な変更が漏れていないか
- **境界条件でロジックが破綻しないか。** 対象のクラス名と、想定される境界（0件、同点、ちょうど閾値、
  nil、既存機能との組み合わせ）を具体的に列挙して渡す
- **テストが挙動を実際に検証しているか。** 変異テスト（定数や条件を書き換えて spec が落ちるか）で
  確認するよう指示する。CI が緑であることと、変更した挙動を固定できていることは別

変更内容に応じて足す観点:

| 変更の種類 | 足す観点 |
| --- | --- |
| 画面表示を伴う | 他の画面（マイページ / `/preferences`）との一貫性。同じユーザーに矛盾した情報を出さないか |
| 画面表示を伴う | スマートフォン幅での破綻。詳細は `mobile-check` スキル |
| 文言の変更 | 想定ユーザーは初心者。専門用語や、データが裏付けない断定表現になっていないか |
| 依存関係の更新 | 記載バージョンと lockfile の実値が一致するか。メジャー更新の破壊的変更 |

### 3. 出力形式

以下を指定する。**忖度は不要**と明示し、問題がなければ「指摘なし」と明記させる。

```
- **重大な問題**: マージ前に必ず直すべきもの（無ければ「なし」）
- **改善提案**: 直した方がよいが必須ではないもの（無ければ「なし」）
- **良い点**: 簡潔に

各指摘には根拠となるファイル名・行番号・実行結果を添えること。
```

## 指摘を受け取ったあと

**鵜呑みにしない。** 重大な問題として挙がったものは、**自分で再現を確認してから**修正する。
サブエージェントが誤解している場合もあるため、再現しないものは対応しない。

修正したら、**同じ変異テストを自分でも回して**指摘が本当に解消したか確かめる。
「spec を足した」だけでは、その spec が挙動を固定できているとは限らない。

対応が終わったら、何を指摘されどう直したか、そして取り込まなかった指摘とその理由を PR 本文に追記する
（CLAUDE.md の「PR レビュー」参照）。指摘が妥当でも、スコープ外なら別 Issue に
切り出す方が適切なことがある。

## 再レビュー（重大な問題を修正した場合のみ、1回だけ）

1回目で**重大な問題**が指摘され、それを修正したときだけ、もう1回だけレビューさせる。
修正コミットは元の実装と同じかそれ以上に危ないため、そこだけを見てもらう。

- **PR 全体を最初から調べ直させない。** 見るのは**重大指摘への修正差分だけ**。
  `git log --oneline main..HEAD` で修正コミットを特定し、`git show <sha>` の内容を渡して
  「この差分が、指摘された問題を実際に解消しているか」だけを確認するよう指示する
- **新しいサブエージェントを呼ぶ。** 同じエージェントに続けさせると、自分が出した指摘への
  修正を自分で評価することになる
- **1回目で何が指摘され、どう直したかを伝える。** 確認の的を絞るため
- ここで新しい指摘が出ても**3回目は行わない**。内容をユーザーに報告して判断を仰ぐ

## やらないこと

- 指摘が0件でも、それを理由に目視確認を省かない。サブエージェントは実際の画面を見ていない
- **合計3回目のレビューを始めない。** 指摘が残っていてもユーザーに報告して止める
- PR を作成しただけでこのスキルを起動しない。ユーザーの明示的な依頼を待つ
